# Deploying Presence on Coolify

This guide walks through installing the Presence app (repo: `dblue-tech/booking-app`) on a Coolify instance. It assumes Coolify is already running and reachable, and that you have push/admin access to the repository and to the domain's DNS.

## 1. Architecture in one paragraph

Presence is a monorepo with two independent pieces: a Node/Express backend (REST API + WebSocket server) and a React/Vite frontend (static SPA). On Coolify they are deployed as **two separate applications**, each built from its own `Dockerfile` in the repo (`backend/Dockerfile`, `frontend/Dockerfile`) — not merged into a single service. They must be published on **two subdomains of the same root domain** (e.g. `app.dblue.it` for the frontend, `api.dblue.it` for the backend) — this is what lets the backend's authentication cookie be shared safely between the two without being treated as a third-party cookie by the browser. The database is **MongoDB Atlas**, never a self-hosted Mongo instance — the app relies on Change Streams for real-time updates, which require a replica set that Atlas provides out of the box (even on the free M0 tier) and a bare standalone MongoDB does not.

```
                 ┌────────────────────┐
   Browser  ───▶ │ app.<root-domain>  │  frontend application (nginx, static build)
                 └─────────┬──────────┘
                           │ REST + WebSocket, same-site cookie
                 ┌─────────▼──────────┐
                 │ api.<root-domain>  │  backend application (Node/Express)
                 └─────────┬──────────┘
                           │
                 ┌─────────▼──────────┐
                 │   MongoDB Atlas    │  replica set (Change Streams)
                 └─────────────────────┘
```

## 2. Prerequisites

- A Coolify project with the GitHub source connected (or the repo added as a public/private Git source).
- A MongoDB Atlas cluster (M0 is enough for staging; M10+ for production), with a database user and connection string ready.
- A Google Cloud OAuth 2.0 Client (Web application type) — one set of credentials per environment is recommended (don't reuse staging credentials in production).
- Control of the DNS for the root domain (to point subdomains at the Coolify server).

## 3. Create the two Coolify applications

Repeat this twice — once per app. In Coolify: **New Resource → [Public/Private] Repository**, select `dblue-tech/booking-app` and the branch to deploy (`main`).

### 3.1 Backend application

| Setting | Value |
|---|---|
| Build Pack | `Dockerfile` |
| Base Directory | `backend` |
| Dockerfile Location | `Dockerfile` |
| Ports Exposes | `4000` |
| Health Check Path | `/health` |

### 3.2 Frontend application

| Setting | Value |
|---|---|
| Build Pack | `Dockerfile` |
| Base Directory | `frontend` |
| Dockerfile Location | `Dockerfile` |
| Ports Exposes | `80` |
| Health Check Path | `/` |
| Build Argument | `VITE_API_URL` = the backend's public URL (see §5) |

`VITE_API_URL` **must** be a build argument, not just a runtime environment variable — Vite bakes it into the static bundle at build time, so it has to be known and correct *before* the frontend image is built.

## 4. Environment variables

Set these in each application's **Environment Variables** panel in Coolify. Nothing here is auto-generated by Coolify (unlike some platforms that inject a database URL automatically) — every value below is set by hand.

### 4.1 Backend

| Variable | Required | Notes |
|---|---|---|
| `MONGODB_URI` | Yes | Atlas connection string. |
| `JWT_SECRET` | Yes | Random string, 32+ chars — generate with `openssl rand -base64 32`. |
| `GOOGLE_CLIENT_ID` | Yes | From the Google Cloud OAuth client. |
| `GOOGLE_CLIENT_SECRET` | Yes | Same client — never expose this to the frontend. |
| `APP_URL` | Yes | Public URL of the frontend application (e.g. `https://app.dblue.it`). Used as the CORS origin — must match exactly, no trailing slash. |
| `BACKEND_URL` | Yes | Public URL of this backend application (e.g. `https://api.dblue.it`). Used to build the Google OAuth callback URL. |
| `PORT` | Yes | `4000` — must match "Ports Exposes" above. |
| `NODE_ENV` | Yes | `production` — set this in **both** staging and production; it controls Node/Express performance behavior, not which environment this is. |
| `APP_ENV` | Yes | `staging` or `production` — the actual environment label, kept separate from `NODE_ENV` on purpose. |
| `COOKIE_DOMAIN` | Yes | `.dblue.it` (the shared root domain, **identical value in every deployed environment** — staging and production alike, since the root domain never changes, only the subdomain prefix does). This is the setting that makes the shared-domain authentication cookie work; see §6. |
| `ENABLE_DEV_LOGIN` | Staging only | `true` to allow the password-based dev login screen for internal testing. Leave unset (or `false`) in production. |
| `DEV_LOGIN_USER` / `DEV_LOGIN_PASS` / `DEV_LOGIN_NAME` / `DEV_LOGIN_ROLE` | Only if `ENABLE_DEV_LOGIN=true` | Credentials for the dev-login account. |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` / `SMTP_PASS` / `SMTP_FROM` | Optional | If omitted, outgoing emails are logged instead of sent — fine for staging. |
| `DBLUE_OFFICE_API_URL` / `DBLUE_OFFICE_API_KEY` | Optional | dblue-office integration; off by default, toggled at runtime from the app's admin panel. Not required for a first deploy. |

### 4.2 Frontend

| Variable | Required | Notes |
|---|---|---|
| `VITE_API_URL` | Yes (build arg, §3.2) | Public URL of the backend application. |
| `VITE_DEV_LOGIN_ENABLED` | Staging only | `true` to show the dev-login form. Never `true` in production. |

## 5. Domains and TLS

In each application's **Domains** tab, add the subdomain for that app (e.g. `app.dblue.it` for the frontend, `api.dblue.it` for the backend). Point a CNAME for each subdomain at the Coolify server in your DNS provider. Coolify provisions a TLS certificate automatically (Let's Encrypt, via its built-in Traefik proxy) once the DNS resolves — no manual certificate work needed.

> The exact subdomain prefixes for a non-production environment (e.g. a staging deploy) are up to you — what matters is that **both applications sit under the same root domain**, so choose a scheme once and use it consistently (for example `staging-app.dblue.it` / `staging-api.dblue.it`).

## 6. Why the shared domain matters (short version)

The backend issues an `httpOnly` session cookie. Browsers increasingly block cookies set by one domain from being read while browsing a *different* domain, even with permissive cookie settings — this is "third-party cookie" blocking (Safari ITP, and an ongoing Chrome rollout), and it does not depend on classic CORS/SameSite configuration. Putting the frontend and backend on subdomains of the same root domain (`app.` / `api.` under `dblue.it`) makes them "same-site" to the browser, so the cookie — set with `Domain=.dblue.it` and `SameSite=Lax` — is treated as first-party by both. This is exactly what `COOKIE_DOMAIN` in §4.1 turns on; without it, the backend falls back to today's Railway-era behavior (`SameSite=None`, unrelated domains), which is why setting it correctly is the one variable that most affects whether login actually works end to end.

## 7. First deploy checklist

- [ ] Both applications created, pointed at `dblue-tech/booking-app`.
- [ ] Environment variables set on both (§4) — `COOKIE_DOMAIN` identical on the backend across every environment.
- [ ] Domains added and DNS CNAMEs pointed at the Coolify server (§5); TLS certificates issued (visible as green/active in Coolify).
- [ ] Google OAuth client's redirect URI updated to `https://<backend-domain>/auth/google/callback`.
- [ ] MongoDB Atlas cluster reachable from Coolify — if Atlas's IP access list is restricted, allow the Coolify server's outbound IP (or `0.0.0.0/0` for a quick first deploy, tightened later).
- [ ] `GET https://<backend-domain>/health` returns `{"status":"ok", ...}`.
- [ ] Frontend loads at `https://<frontend-domain>/`, login completes, and the app reaches the main screen.
- [ ] A second browser session shows presence updates pushed live (confirms the WebSocket connection).

## 8. Troubleshooting

| Symptom | Likely cause |
|---|---|
| Login redirects back to the login screen instead of staying signed in | `COOKIE_DOMAIN` unset or wrong on the backend, or `APP_URL`/`BACKEND_URL` don't exactly match the real public URLs. |
| CORS error in the browser console | `APP_URL` on the backend doesn't exactly match the frontend's origin (protocol + host, no trailing slash). |
| Backend can't reach MongoDB | Atlas IP access list doesn't include the Coolify server, or `MONGODB_URI` has a typo/wrong credentials. |
| Container keeps restarting / marked unhealthy | "Ports Exposes" and "Health Check Path" don't match what's actually served — see §3 tables. |
| Presence updates don't appear live in a second tab | WebSocket connection blocked — check that Coolify's proxy isn't stripping the `Upgrade` header (default Coolify/Traefik setup handles this; only relevant if a custom reverse proxy sits in front). |
